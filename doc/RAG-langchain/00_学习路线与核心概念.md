# 00 学习路线与核心概念

## 1. RAG 要解决什么问题？

大语言模型可以根据训练中学到的知识回答问题，但不天然知道某个企业的最新制度，也不能仅凭记忆得知一张报销单的审批状态。

RAG 把外部知识引入回答过程：先获取相关资料，再让模型基于这些资料作答。这里的“外部知识”既可以来自文档，也可以来自数据库、API 或知识图谱。

```text
用户问题 → 检索外部知识 → 构造上下文 → 模型回答
```

RAG 不自动保证知识实时。制度文件未更新、索引未同步，模型仍可能收到旧资料。也不能仅凭“回答带了引用”就断定它正确，需要核对引用是否支持结论。

## 2. 先区分检索与生成

以“P6 员工去上海住宿一晚能报销多少”为例：

- 检索负责找到适用年份、职级、城市的额度条款。
- 上下文处理负责保留条件、金额和来源，减少无关内容。
- 生成负责把证据整理成可读的回答。

如果根本没有找到正确条款，通常应先改检索；如果条款找对了但回答引用了另一城市的金额，应检查上下文组织和生成过程。

## 3. LangChain 提供什么？

LangChain 提供搭建这些流程的接口与组件。学习时可以先建立以下对应关系：

| 概念 | 常见 Python 接口 | 作用 |
| --- | --- | --- |
| 文档 | `Document` | 保存正文和来源信息 |
| 分块 | `RecursiveCharacterTextSplitter` | 将长文本分为可检索片段 |
| 向量化 | Embeddings 接口 | 把文本转换为数值向量 |
| 向量存储 | VectorStore 接口 | 存储向量并执行相似度检索 |
| 检索器 | Retriever 接口 | 接收查询，返回文档 |
| 聊天模型 | ChatModel 接口 | 接收消息，输出回答或工具调用 |
| 工具 | `@tool` | 将函数声明为模型可调用能力 |
| 智能体 | `create_agent` | 管理模型和工具的调用循环 |

例如，一条文档可以这样表达：

```python
from langchain_core.documents import Document

doc = Document(
    page_content="P6员工到上海出差，住宿上限为每晚600元。",
    metadata={"source": "现行住宿额度表", "id": "limit-p6-sh"},
)
```

这只是数据对象，没有发生模型调用。`metadata` 也不会自动参与语义匹配或被模型看到；是否过滤、是否写入上下文，需要流程显式处理。

官方参考：[语义检索教程](https://docs.langchain.com/oss/python/langchain/knowledge-base)。

## 4. LangGraph 提供什么？

LangGraph 适合管理有状态的处理流程。可以把任务拆成节点，用边指定连接方式，再依据状态选择分支或回到前一步。

```text
检索 → 评估证据
         ├─ 充分 → 回答
         └─ 不足 → 改写查询 → 再检索
```

LangChain 的 `create_agent` 已建立在 LangGraph 之上。简单的工具调用循环可以先使用 LangChain；需要精确控制评估、重试、状态和分支时，再直接使用 LangGraph。

官方参考：[Agents](https://docs.langchain.com/oss/python/langchain/agents)、[Graph API](https://docs.langchain.com/oss/python/langgraph/graph-api)。

## 5. 阅读后续教程时应注意什么？

每增加一个步骤，都追问它解决了哪种失败：查询改写针对表达问题，重排针对候选选择，模块化针对能力组织，图结构针对关系检索，Agent 针对运行时决策。

正文代码使用 Python 接口示意。比如 `model` 表示已配置的聊天模型，`retriever` 表示已配置的检索器；不同课程不会要求共享一个目录里的隐藏辅助函数。模型供应商的实例化方式可参考 [ChatOpenAI 集成](https://docs.langchain.com/oss/python/integrations/chat/openai) 等官方页面。
