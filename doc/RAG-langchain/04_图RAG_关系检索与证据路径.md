# 04 图 RAG：关系检索与证据路径

## 1. 为什么文档检索有时不够？

问题是“E001 去上海出差，住宿每晚最多报销多少”。员工记录保存 E001 的职级，制度表按职级与城市规定额度。两个来源各自只包含答案的一部分。

Graph RAG 用实体、关系和路径组织知识，帮助系统找到连接这些信息的证据。

```mermaid
flowchart LR
    E[员工E001] -->|职级| G[P6]
    G -->|适用城市：上海| P[住宿额度条款]
    P -->|每晚上限| M[600元]
```

这里每条关系都应有数据来源。“E001 属于 P6”来自员工记录，“P6 在上海为 600 元”来自制度，不能只是模型认为它们可能有关。

## 2. Graph RAG 改变了哪一层？

它主要改变知识表示和检索方式。基础文档检索返回语义相近的片段，图检索还能利用节点之间明确的关联。

| 检索角度 | 可以获得的信息 |
| --- | --- |
| 文本相似度 | 哪些段落与住宿报销相关？ |
| 图关系 | 这个员工适用哪一职级、哪一城市的额度？ |
| 两者结合 | 关系路径对应的原始条款和完整适用条件是什么？ |

并非所有 Graph RAG 都以同样方式建图。有的从文本抽取实体关系，有的直接使用业务关系数据，还有的对图做聚合摘要。本课聚焦最容易理解的关系路径检索。

## 3. 如何设计图数据？

先确定实体，例如员工、职级、城市、制度版本、额度条款；再定义关系及属性，例如“属于职级”“适用城市”“生效时间”。

通常需要处理四类问题：

1. 同名实体如何区分，例如不同部门同名员工。
2. 关系来自哪条原始记录，能否追溯。
3. 制度过期后怎样更新关系，避免新旧额度混合。
4. 用户查询是否在图的覆盖范围内。

图中没有深圳额度时，应说明缺少关系数据，不能沿相似城市的路径得出结论。

## 4. Python 中的最小关系示意

下面用 NetworkX 表达路径，仅说明关系检索原理：

```python
import networkx as nx

graph = nx.DiGraph()
graph.add_edge("E001", "P6", relation="职级", source="员工记录")
graph.add_edge("P6", "上海额度条款", city="上海", source="现行制度")

for grade in graph.successors("E001"):
    for clause in graph.successors(grade):
        if graph[grade][clause]["city"] == "上海":
            print(grade, clause)
```

真实查询需要先检查实体存在性，返回关系对应的原文，并保留来源。这段示意未包含自动实体识别、金额解析和图谱维护。

## 5. 怎样接入 LangChain？

将图查询返回的路径与条款转换为 `Document` 列表，就能复用前面的上下文构造与生成步骤。

```text
问题 → 实体识别与条件提取 → 图查询
  → 员工职级证据 + 适用额度条款
  → 整理来源 → 模型回答
```

如果使用 Neo4j，可以使用 LangChain 的相关集成。自然语言生成 Cypher 是一种可选方式，但图 RAG 并不要求必须让模型生成查询；固定查询或受控查询模板同样能利用图关系。[官方 Neo4j 集成](https://docs.langchain.com/oss/python/integrations/graphs/neo4j_cypher)

## 6. 与 LangGraph、Agentic RAG 的关系

LangGraph 中的图通常描述执行流程，例如“检索→评估→重试”。Graph RAG 中的图描述知识关系，例如“员工→职级→额度”。使用 LangGraph 并不自动获得知识图谱。

图检索还可以作为一个工具交给 Agent。这样，图负责提供关系证据，Agent 负责决定何时查图、何时查文档以及是否继续补充。

思考：若员工职级数据过期，图路径再完整，结论是否可靠？图结构不能替代数据质量。
