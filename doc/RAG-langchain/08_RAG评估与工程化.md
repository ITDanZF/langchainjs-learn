# 08 RAG 评估与工程化

## 1. 怎样判断 RAG 的改进有效？

“能生成答案”和“能可靠完成任务”是不同层次。评估应分别检查资料检索、上下文、最终答案和智能体过程，才能确定应改哪一部分。

| 层次 | 核心问题 |
| --- | --- |
| 检索 | 正确来源是否进入候选，是否排在前面？ |
| 上下文 | 条件、数字、来源是否保留，有无冲突与噪声？ |
| 生成 | 结论是否正确，能否被证据支持？ |
| Agent过程 | 工具和参数是否正确，是否存在无效循环？ |
| 效率 | 耗时、模型与工具调用数、token 用量如何？ |

官方参考：[RAG evaluation](https://docs.langchain.com/langsmith/evaluate-rag-tutorial)。

## 2. 先准备可复查的问题集

不要只测试最容易回答的“P6 上海额度是多少”。还应覆盖：

- 不同说法：住酒店、住宿费、差旅额度。
- 条件变化：P6/P7、上海/北京、当前/历史年份。
- 多跳问题：从员工 ID 找职级，再查询额度。
- 缺失条件：只问“我能报销多少”，未提供职级或城市。
- 无答案问题：知识库没有相应地区制度。
- 冲突资料：多个版本、不同适用范围。

为每题标注必要来源、可接受结论和应说明的缺口。多跳题要标注全部必要来源，只找到额度表而没有员工职级关系，不算证据链完整。

## 3. 常见检索指标

### Recall@K

前 K 条结果覆盖了多少标注相关资料：

```text
Recall@K = 前K条中的相关资料数 / 全部标注相关资料数
```

### Precision@K

前 K 个结果位置中相关资料的比例：

```text
Precision@K = 前K条中的相关资料数 / K
```

结果不足 K 条时，需要明确评估约定。若固定以 K 为分母，空缺位置按未命中处理；若按实际返回数计算，应另行说明。

### MRR@K

取第一个相关结果排名的倒数，再对问题求平均。相关资料排第 1 位得 1，排第 2 位得 1/2，没有命中得 0。

例如，唯一相关资料是 A，前三条是 `[B, A, C]`，则 Recall@3=1、Precision@3=1/3、该题倒数排名为 1/2。

MRR 反映第一个相关结果的位置，不能单独判断多跳问题所需证据是否齐全。还应明确指标是按片段还是按原始文档计算，避免重复片段影响比较。

## 4. 怎样评估答案和引用？

逐条拆出答案中的事实，寻找对应证据。例如：

| 答案结论 | 需要的来源 |
| --- | --- |
| E001 是 P6 | 员工记录 |
| P6 到上海上限为每晚600元 | 对应年份额度条款 |
| R001 仍在审批中 | 报销单状态记录 |
| 两晚合计上限为1200元 | 额度、晚数及正确计算 |

检查来源 ID 是否存在只是第一步，还要看内容是否真正支持该结论。“引用了一篇包含600元的文档”不等于适用职级和地区正确。

LLM 评估器可以辅助筛查，但也会误判。应先用人工标注校准，再用于扩大样本，不能把评估模型当作天然正确的裁判。

## 5. 怎样评估 Agent 的过程？

对同一个问题记录工具名、参数、返回证据、后续决策与停止原因。特别检查：

- 是否查询了不存在的 ID 后继续猜测。
- 是否重复相同检索且未获得新资料。
- 是否取得必要证据后仍不断调用工具。
- 是否在证据不足时说明缺口。
- 多 Agent 之间是否遗漏了城市、年份或来源。

LangSmith 可帮助追踪调用过程，LangGraph 可暴露节点与状态变化。追踪能力方便诊断，不会自动保证流程正确。

## 6. 怎样做有解释力的对照？

比较向量检索和混合检索时，先固定语料、问题、过滤条件和输出 K；比较重排时，明确召回候选规模。避免同时更换模型、切块、语料版本和提示，导致无法判断收益来自哪里。

分别记录建索引耗时、查询耗时和端到端回答耗时。若评估只测检索，不应将结果称为整个 Agent 的响应时间。

高级方法并不保证每次更好。基础系统已经答对的短问题，增加重排或多个 Agent 可能仅增加延迟与用量。

## 7. 从原理到真实应用，还要补哪些设计？

| 方面 | 应考虑的内容 |
| --- | --- |
| 数据 | 解析质量、表格条件、来源与版本 |
| 索引 | 持久化、更新、删除同步、embedding变更 |
| 数据访问 | 用户身份、允许访问的记录、查询超时 |
| 控制 | 重试策略、检索轮数、总调用预算 |
| 状态 | 会话隔离、checkpoint、恢复后的行为 |
| 证据 | 来源存在性、结论支持程度、冲突处理 |
| 反馈 | 错误样本收集、回归评估与改进追踪 |

LangGraph 的 [持久化能力](https://docs.langchain.com/oss/python/langgraph/persistence) 可以保存执行状态，但保存聊天历史不等于自动具备高质量长期记忆检索，仍需要明确何时写入、如何检索与更新。

学习时可以从一条可解释的基础流程开始，先识别最主要的失败类型，再决定增加重排、关系图或智能体决策。每次新增能力都应有可观察、可评估的用途。
